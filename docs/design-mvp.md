# 电商系统第一阶段 MVP 设计说明

## 目标

第一阶段只完成基础购物闭环，确保工程可运行、前后端可独立启动，并为后续业务模块预留清晰边界。

## MVP 范围

- 用户登录
- 商品列表与商品详情
- 购物车
- 地址管理
- 确认订单
- 提交订单
- 模拟支付
- 订单列表与订单详情
- 后台商品管理
- 后台订单管理

## 暂不实现

- 优惠券、积分
- 售后、退款、财务对账、分账
- 精细权限、操作日志、导出
- 自动化测试平台、质量大屏

## 生产化补充建议

### 建议 21：后台关键操作增加审计日志、权限和操作约束

MVP 阶段暂不实现精细权限、操作日志和导出，但生产化后台必须补齐审计、权限边界和高风险操作约束。审计日志用于追溯“谁在什么时间、从哪里、因为什么原因，把哪个业务对象从什么状态改成了什么状态”，不能只记录简单菜单点击或模块动作。

必须纳入审计的关键操作包括：

- 商品新增、编辑、上下架。
- SKU 改价。
- SKU 改库存。
- 订单发货。
- 修改物流。
- 售后审批。
- 售后拒绝。
- 人工退款。
- 库存修复。
- 优惠券发放。
- 积分调整。

审计日志建议字段：

| 字段 | 说明 |
| --- | --- |
| `operatorId` | 后台操作人 ID。 |
| `operatorName` | 后台操作人名称或账号。 |
| `operationType` | 操作类型，例如 `PRODUCT_CREATE`、`SKU_PRICE_UPDATE`、`ORDER_SHIP`。 |
| `bizType` | 业务对象类型，例如 `PRODUCT`、`SKU`、`ORDER`、`AFTERSALE`、`COUPON`、`POINT`。 |
| `bizId` | 业务对象 ID。 |
| `beforeValue` | 操作前快照，建议使用 JSON。 |
| `afterValue` | 操作后快照，建议使用 JSON。 |
| `reason` | 操作原因，高风险操作必填。 |
| `ip` | 操作来源 IP。 |
| `userAgent` | 操作来源客户端信息。 |
| `createdAt` | 审计日志创建时间。 |

生产化验收要求：

- 审计写入必须与业务变更在同一事务或具备可靠补偿，不能出现业务已改但审计缺失。
- 高风险操作必须校验权限，并要求填写原因；原因不得由前端静默默认。
- `beforeValue` 和 `afterValue` 只记录必要业务字段，避免写入密码、Token、手机号全量明文等敏感信息。
- 审计日志只能追加，后台页面不提供删除或编辑能力；如需订正，应追加新的订正记录。
- 查询侧至少支持按操作人、操作类型、业务类型、业务 ID 和时间范围筛选。
